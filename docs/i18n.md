# FaraCart — Internationalization (i18n)

> **Phase 27 / Tasks P27-T01–T04.** FaraCart is translation-ready end to end:
> WordPress translation functions with the `faracart` text domain, a POT
> extraction/build pipeline (PHP + the React admin app), full RTL support,
> and locale-aware number/currency/date formatting. Persian is supported
> well — RTL mirroring, Persian digits and proper plural rules — without a
> single hard-coded Persian string in the source.

---

## 1. Text domain (P27-T01)

- **Domain:** `faracart`, declared in the plugin header
  (`Text Domain: faracart`, `Domain Path: /languages`) — verified by
  `tests/wordpress-compatibility-test.php`.
- **Loading:** `Plugin::load_textdomain()` calls
  `load_plugin_textdomain( 'faracart', false, dirname( FARACART_BASENAME ) . '/languages' )`
  on the `init` hook.
- **PHP layer:** every user-facing string uses `__()`, `_e()`,
  `esc_html__()`, `esc_attr__()`, `_x()`/`_ex()` or `sprintf()` with the
  `faracart` domain — REST errors, admin menus, the message engine,
  reward labels, compatibility notices, cron labels. `tests/i18n-test.php`
  scans the whole PHP tree and fails on any domain-less call.
- **React admin:** `admin-app/src` imports `__` / `_x` / `_n` / `sprintf`
  from `@wordpress/i18n`; Vite aliases that package to
  `admin-app/src/lib/wp-i18n.ts`, a drop-in shim that delegates to the
  `wp.i18n` global WordPress core ships. The admin script declares
  `wp-i18n` as a dependency and `AssetLoader::finish_enqueue()` calls
  `wp_set_script_translations( 'faracart-admin', 'faracart', FARACART_PATH . 'languages' )`,
  so locale JSON lands straight in `wp.i18n.setLocaleData()`.

## 2. POT generation & build pipeline (P27-T02)

The reference plugin's `makepot` / `i18n:*` npm-script convention,
implemented without wp-cli:

| Script | Runs | Purpose |
|---|---|---|
| `npm run makepot` / `i18n:extract` | `php bin/extract-pot.php` | Scans `ravis-faracart.php`, `includes/` (PHP) and `admin-app/src` (TS/TSX — same `__( '…', 'faracart' )` syntax) and writes `languages/faracart.pot` — deterministic (sorted, deduped, `#: file:line` references). |
| `npm run i18n:verify` | `php bin/extract-pot.php --check` | Exits 1 when the committed POT is out of date with the source (CI guard). |
| `npm run i18n:build` | `php bin/build-i18n.php` | For every `languages/faracart-<locale>.po`, compiles a gettext `.mo` and the JED JSON the admin app loads (`faracart-<locale>-faracart-admin.json`, the `{domain}-{locale}-{handle}.json` name `load_script_textdomain()` looks for — verified against WP 7.0). |
| `npm run i18n:all` | extract + verify + build | Full pipeline in one command. |

`languages/faracart.pot` is committed (727 entries). Translators copy it to
`faracart-<locale>.po`, fill in `msgstr`, and run `npm run i18n:all`; the
`.mo` covers the PHP strings and the JED JSON translates the React admin.
No wp-cli, gettext tooling or node packages are required — the build is a
plain PHP script.

## 2b. Shipped translation: Persian (fa_IR)

`languages/faracart-fa_IR.po` ships translations for the key
customer-facing storefront strings (message-engine states, reward labels,
the cart fee label and the block copy) **and the entire WordPress admin
dashboard** — every string referenced from `admin-app/src` (nav,
analytics, the revenue section, goal/campaign builders, settings,
appearance, previews, empty states, confirmations, toasts, …), plus the
storefront/REST PHP strings, for a 727-entry file that exactly mirrors
`languages/faracart.pot`. Compiling it produces:

> **Keeping it in sync:** when a new phase adds strings to the POT, merge
> the new entries into the `.po` and keep the existing `msgstr` lines — do
> **not** `cp` the POT over the `.po`, or all 727 translations are lost.
> `tests/i18n-test.php` fails on any admin-app string missing a
> translation, so a full merge is required before the suite turns green.

- `languages/faracart-fa_IR.mo` — loaded by the PHP layer.
- `languages/faracart-fa_IR-faracart-admin.json` — JED JSON for the React
  admin handle.

Since WP 6.5, `load_plugin_textdomain()` no longer loads a file directly:
it registers the languages path in `WP_Textdomain_Registry` and the first
`__()` call triggers a just-in-time load of `faracart-<locale>.mo`. Two
consequences worth knowing:

- The `.mo` activates automatically for the site locale — no cache busting
  needed.
- Do **not** call `unload_textdomain( 'faracart' )` and then expect a
  re-registered `load_plugin_textdomain()` to pick up a new locale: the
  JIT loader permanently short-circuits domains marked unloaded
  (`$l10n_unloaded`). `tests/i18n-test.php` therefore verifies the fa_IR
  flow the same way a real request behaves: `switch_to_locale()` →
  `Plugin::load_textdomain()` → `__()`.

`tests/i18n-test.php` (section 1b) asserts the `.po` carries all key
storefront strings **and every admin-dashboard string referenced from the
POT** (a coverage scan — a new admin string without a translation fails
the suite), the `.mo`/`.json` artifacts exist, the JED carries Persian
dashboard labels, and the strings resolve to Persian end-to-end through
the real loading path.

Suites that assert English storefront strings (`message-test.php`) force
`switch_to_locale( 'en_US' )` + `unload_textdomain( 'faracart' )` first,
so they stay deterministic on fa_IR installs with a shipped `.mo`.

## 3. RTL (P27-T03)

- **Admin dashboard** — the three-part MUI setup: the PHP mount point sets
  `dir="rtl"` from `is_rtl()` (`Admin`), the MUI theme direction flips on
  `boot.isRtl` (`theme/index.ts`), and the Emotion cache is RTL-flipped via
  `@mui/stylis-plugin-rtl` (`AppProviders.tsx`). Boot data carries
  `isRtl`.
- **Storefront** — the widget config prints `isRtl` and the stylesheet
  uses logical properties throughout (`inset-inline`, `margin-inline`,
  `border-inline-start`, …) — verified by the i18n test asserting the CSS
  has zero physical `left`/`right` properties, so the widgets mirror
  automatically in RTL locales.
- Verified by `tests/wordpress-compatibility-test.php` (dir attribute +
  `isRtl` config) and `tests/i18n-test.php` (setup + CSS).

## 4. Locale-aware number / currency / date formatting (P27-T04)

- **Storefront** — `ProgressUI::frontend_config()` now carries `locale`
  (`get_locale()`); `assets/js/frontend.js` derives a BCP-47 tag
  (`fa_IR` → `fa-IR`) and passes it to `Intl.NumberFormat` in
  `formatMoney()` / `formatNumber()`. Persian locales therefore render
  Persian digits and separators (`۲۵۰٬۰۰۰`) instead of the browser
  default locale — verified behaviorally with Node:
  `new Intl.NumberFormat('fa-IR').format(1234.5)` → `۱٬۲۳۴٫۵`.
- **Admin** — `lib/format.ts` formats money/numbers with
  `Intl.NumberFormat( boot.locale.replace('_','-') )`; the date range
  (`date-range/dateRange.ts`, `CustomRangePicker`) and the analytics
  charts format dates with `Intl.DateTimeFormat( boot.locale … )`.
- **PHP** — money in the message engine renders through `wc_price()`
  (WooCommerce already applies the site locale and digits); timestamps are
  stored with `current_time()` (timezone-aware) and user-facing dates are
  rendered client-side via Intl.
- **No hard-coded Persian** — `tests/i18n-test.php` scans every PHP/TS/JS
  source file for Persian/Arabic script characters and fails on any hit;
  Persian support comes from the translation files and the locale-aware
  formatters above.

## 5. Adding a language

1. `cp languages/faracart.pot languages/faracart-fa_IR.po`
2. Translate the `msgstr` lines (keep `%s`/`%d` placeholders and
   `{variable}` tokens intact).
3. `cd admin-app && npm run i18n:all`
4. Commit the `.po`, `.mo` and `.json` files. The locale activates
   automatically once WordPress is set to that locale.
